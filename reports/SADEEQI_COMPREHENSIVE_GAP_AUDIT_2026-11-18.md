- لا يوجد في الأدلة الحالية APK حديث مبني من هذا الالتزام ومثبت ومختبر على هاتف فعلي.
- لا يوجد إثبات حديث لنشر Cloudflare Worker بعد تغيير الاسم على الفرع، ولا لاختبار POST /v1/chat بمصادقة صحيحة.
- تقرير 14 نوفمبر السابق سجل HTTP 200 لمسار Vercel health، لكنه لم يثبت دردشة مصادق عليها، وسجل عائق Vercel build-rate-limit.
- لا ينبغي دمج PR #41 أو أي PR متداخل قبل حل التعارضات الوظيفية والتحقق من الاختبارات والبناء.

## 3. سجل الفجوات حسب الأولوية

### P0 — مانعات التسليم

| المجال | الفجوة / الدليل | المطلوب لإغلاقها |
|---|---|---|
| CI / GitHub Actions | آخر Android/backend/security jobs فشلت بلا خطوات أو سجلات ظاهرة | الحصول على سجل تشغيل قابل للقراءة أو تشغيل نفس الأوامر في Runner بديل؛ تحديد هل الفشل قبل بدء Runner أم أثناء checkout/setup |
| Android build | لا يوجد APK حديث موثق من HEAD الحالي | تشغيل unit tests ثم assembleDebug، حفظ artifact، التحقق من SHA-256 وحجم الملف وتثبيته |
| Supabase build config | workflow الحالي على main يرفض البناء إذا غاب `SADEEQI_SUPABASE_URL` أو `SADEEQI_SUPABASE_ANON_KEY` | التأكد من وجود القيم في إعدادات CI دون كشفها؛ لا تستخدم placeholders في APK تسليم |
| Backend auth | كود Vercel/Worker يدعم أوضاع legacy/dual/supabase؛ إعدادات الإنتاج الفعلية الحالية غير مثبتة | اختيار وضع المصادقة المقصود والتحقق من `SUPABASE_URL` وJWKS واختبار جلسة مستخدم حقيقية |
| AI provider | Worker الحالي افتراضياً Groq ويتطلب `GROQ_API_KEY`؛ إعدادات Cloudflare الموثقة سابقاً لم تثبت وجوده | فحص أسماء المتغيرات فقط داخل لوحة الخدمة، وضبط مزود مجاني متاح دون نسخ أي مفاتيح إلى المحادثة؛ اختبار استجابة فعلية |
| Production deployment | لا يوجد إثبات نشر Worker بعد مواءمة الاسم؛ Vercel سبق أن واجه build-rate-limit | نشر مقصود بعد CI، ثم اختبار health وطلب دردشة مصادق عليه |
| Device acceptance | لا يوجد اختبار حديث على هاتف فعلي | تثبيت APK الناتج واختبار الدخول والدردشة والصوت والذاكرة والأذونات والشبكة |

### P2 — جودة وتشغيل وصيانة

1. إضافة lockfile ملتزم به ومراجعة dependency audit على نسخة dependencies ثابتة؛ workflow الأمني الحالي يولد lockfile مؤقتاً ولا يثبت lockfile في المستودع.
2. تشغيل Semgrep وnpm audit وإصلاح النتائج الفعلية، لا تعطيل الفحوص أو تخفيض مستوى الحماية لإظهار اللون الأخضر.
3. فصل CI إلى اختبارات سريعة على PR، واختبارات emulator يدوية/مجدولة إذا كانت تكلفة أو استقرار المحاكي عائقاً.
4. تثبيت عقد API واختبارات توافق بين Android وVercel وCloudflare.
5. إضافة مراقبة آمنة لا تسجل نصوص المحادثات أو المفاتيح، مع request IDs ومقاييس زمن الاستجابة والأخطاء.
6. توثيق سياسة الخصوصية والاحتفاظ بالبيانات وحذف الحساب والذاكرة، قبل أي توزيع عام.
7. إجراء قياسات فعلية لحجم APK واستهلاك RAM والبطارية والبيانات، بدلاً من تقديرات نظرية.

## 4. تعارضات وتبعيات يجب حسمها

- PR #41 يوحّد Worker name فقط؛ لا يثبت أن Worker نُشر أو أن متغيرات بيئته تطابق الكود.
- PR #39 يكرر جزءاً من تغيير اسم Worker، وPR #38 يضيف مسار نشر Cloudflare يتطلب إعدادات سرية/متغيرات في GitHub. يجب تجنب دمج نسخ متكررة من نفس التغيير.
- PR #40 يغيّر سلوك CI للسماح باختبار/بناء دون أسرار حقيقية، لكنه لا يجيز نشر APK غير قابل للاستخدام؛ يجب التأكد من أن artifact النهائي لا ينتج إلا بإعدادات حقيقية.
- PR #35 تجميعي وكبير، ويذكر أن بعض الأعمال مثل إعداد Durable Object واختبار حدود المعدل متعددة النسخ لم تكتمل. لا يُدمج كتلة واحدة دون تفكيك ومراجعة.
- PR #37 يضم تغييرات صوت كثيرة، واختبارات الصوت على الجهاز لا تزال شرط قبول.
- يجب تحديد backend إنتاجي واحد معتمد (Vercel أو Cloudflare) ثم جعل Android وCI والتوثيق تشير إلى نفس الوجهة، أو توثيق خطة failover صريحة.

## 5. خطة المعالجة الهندسية المقترحة

### المرحلة A — استعادة التحقق (أولوية قصوى)
- استخراج سبب فشل الوظائف الأربع من GitHub/CircleCI أو تشغيل نفس الأوامر على Runner بديل.
- تشغيل backend tests واختبار newline الجديد.
- تثبيت lockfile حقيقي ومراجعة الاعتماديات.
- تشغيل Android unit tests وassembleDebug بأسرار Supabase الحقيقية الموجودة في مدير الأسرار فقط.
- حفظ APK artifact مع SHA-256.

**معيار الإغلاق:** جميع الفحوص المطلوبة ناجحة، أو وجود تقرير موثق يميز عطل المنصة عن فشل الاختبار.

### المرحلة B — توحيد النشر والمصادقة
- اختيار backend الأساسي.
- تدقيق أسماء الإعدادات المطلوبة دون قراءة أو كشف قيم الأسرار.
- تفعيل Supabase auth بعد التأكد من الإعدادات، ثم اختبار signup/signin/refresh/chat.
- نشر Cloudflare فقط إذا تقرر اعتماده كهدف فعلي، مع health وauthenticated chat smoke tests.

**معيار الإغلاق:** جلسة مستخدم حقيقية تستطيع إرسال طلب دردشة وتلقي إجابة من مزود AI المحدد.

### المرحلة C — قبول Android على جهاز فعلي
- تثبيت APK من artifact موثق.
- اختبار بدء التشغيل، التسجيل والدخول، المحادثة، العربية صوتاً ونصاً، المقاطعة، رفض الأذونات، انقطاع الشبكة، الذاكرة، الموسيقى، الإشعارات وأوامر الهاتف.
- اختبار ترقية البيانات من الإصدار السابق.

**معيار الإغلاق:** سجل اختبار بتاريخ ونتيجة لكل حالة، مع إصلاح أي عيب مانع.

### المرحلة D — استكمال الميزات
- إكمال wake-word أو إبقاؤه خارج نطاق الإصدار بوضوح.
- إكمال Social OAuth منصة بمنصة وفق موافقات APIs.
- تحسين الصوت الإبي بتقييم متحدثين أصليين، لا بمجرد تسمية إعداد الصوت.
- إكمال التحديثات الموقعة وسياسة الخصوصية ومقاييس الأداء.

## 7. تعريف "جاهز للتسليم"

لن أرفع التقدير إلى 90–100% إلا بعد:
- نجاح backend/security/Android CI.
- إنتاج APK من commit معروف مع SHA-256.
- نجاح تسجيل الدخول والدردشة الفعلية على backend الإنتاجي.
- نجاح اختبارات الهاتف للصوت والذاكرة وأوامر الجهاز.
- توثيق الميزات غير المتاحة بوضوح (wake word، realtime، Social OAuth غير المكتمل، الكتالوج الموسيقي المرخّص).
- اعتماد قرار النشر والدمج وعدم وجود أسرار أو placeholders داخل التطبيق.
